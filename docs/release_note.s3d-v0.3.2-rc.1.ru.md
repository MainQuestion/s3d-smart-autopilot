# s3d Smart Autopilot v0.3.2-rc.1

| | |
|---|---|
| Версия сборки | `v0.3.2-rc.1` (commit `75de75a`) |
| Базовая версия upstream | `s3d v0.3.0` (слито в форк на Go-SDK); прежняя основа `s3d v0.2.1` |
| Рекомендуется | `indexd Smart Autopilot v0.4.1-rc.1` (приём отчётов о попытках и ошибках хостов, размещение Smart); с upstream indexd используется стандартное поведение |
| Предыдущий выпуск | s3d Smart Autopilot v0.3.0-rc.1 (`446c1b5`) |

Второй релиз-кандидат форка s3d. Главное: слияние upstream `s3d v0.3.0` (снапшоты по расписанию, object lock, контрольные суммы, политики бакетов, теги, POST Object, управление пользователями и ключами через admin API) и наши настройки записи, учёт попыток и ошибок хостов.

**Нумерация.** У форка собственная версия, не равная версии upstream: публичная `v0.3.2-rc.1`, приватная сборка `v0.3.2-rc.1-<коммит>`.

## Новое в форке

- **Учёт попыток передачи.** s3d считает по хосту и направлению проигранные гонки, таймауты и отказы подключения и отправляет их в indexd вместе с отчётом о передачах (`POST /hosts/usage`). indexd использует их в отчёте о доле работы хоста и в разборе проблемных хостов.
- **Ошибки хоста.** Ответ хоста с собственной ошибкой считается отдельно от ошибок на стороне клиента, по хосту и направлению, уходит в indexd с тем же отчётом и показывается в `s3d status`.
- **Буферы SDK.** Настройки `uploadMaxBufferedSlabs` (число закодированных slab в памяти на одну загрузку, а значит и число параллельных записей шардов: slab × (data + parity)) и `downloadMaxBufferedChunks` (чанки до 1 МиБ на одно скачивание). `0` оставляет значение SDK (для загрузки около 10 % памяти процесса). Значения видны в `s3d status`, задаются в мастере `s3d config`.
- **Режимы записи шардов.**
  - `uploadRacing` (по умолчанию `true`): если запись шарда на хост медленная, шард параллельно пишется на другой хост. При `false` остаётся только повтор на следующем хосте после ошибки или таймаута.
  - `uploadAttemptTimeoutSeconds`: дедлайн одной попытки записи сектора на хост, после него шард уходит на следующий. `0` значит значение SDK (90 секунд), иначе 5–300.
  - `uploadHedgeBudget`: хеджирование медленных записей вместо гонки по оценке сети. Запись, идущая дольше обычного «хвоста» своего хоста (p(1−budget)), повторяется на следующем хосте, не более чем для этой доли шардов. `0` выключено (по умолчанию), иначе 0,01–0,2. При `uploadRacing: false` хеджирования нет (приоритет у выключенной гонки), в журнал пишется предупреждение.
  - Попытки записи показываются в `s3d status`.
- Всё из v0.3.0-rc.1 остаётся: размещение Smart по Autopilot Mode indexd, собственный `smart-autopilot.log`, отчёты о расходах, замеры скорости, политика избыточности и лимиты передачи.

## Слияние upstream v0.3.0

Слияние выполнено на Go-SDK. Перечень ниже составлен по списку коммитов upstream между `v0.2.1` и `v0.3.0`; детали поведения не перепроверялись нами, кроме указанного в разделе «Проверено».

- Снапшоты: расписание в cron-формате с хранением по календарю (настройка через admin API и командную строку), команда `snapshots restore`, объекты в буфере не попадают в образ снапшота, автоочистка потерянных загрузок при первом старте после восстановления.
- Object lock: конфигурация бакета, retention и legal hold, защита от удаления.
- Политики бакетов, теги бакетов и объектов.
- POST Object (форма и политика).
- Контрольные суммы: `x-amz-checksum-*` для PutObject и UploadPart, составные суммы многочастевых загрузок, проверка при завершении.
- Жизненный цикл: удаление неактуальных версий и просроченных маркеров удаления, фильтры по размеру объекта.
- Управление пользователями и ключами доступа через admin API (команды `users` и `keys` теперь работают через него; в upstream изменение помечено как несовместимое); имена пользователей ограничены набором символов AWS IAM, идентификаторы ключей набором AWS, ответы на некорректные запросы приведены к ответам AWS.
- Автосброс объектов по настраиваемому интервалу, параллельное закрепление загруженных объектов, скорость загрузки считается по прогрессу шардов.
- Исправлен дефект форка: `WithUploadProgress` использовал общий наблюдатель на несколько загрузок (тест падает без исправления).

**Не перенесено** (требует Rust-SDK): регистрация из окружения (`-env`) и предавторизованные ключи при входе. Причина: upstream `v0.3.0` заменил Go-SDK на Rust-обёртку, наши режимы записи (races, noraces, hedge) и клиентское размещение с ней несовместимы, поэтому форк остаётся на Go-SDK.

## Обновление

1. Остановите s3d и сделайте резервную копию каталога данных, **включая `s3d.db` (и `s3d.db-wal`, `s3d.db-shm`, если есть)**, исполняемого файла и конфигурации.
2. Замените исполняемый файл и запустите s3d. В журнале ожидается применение миграций базы (на нашей базе версии 13 → 20, мгновенно) и чистый старт. Если s3d работает как служба с зависимыми службами (например, монтирование диска через rclone), останавливайте и запускайте их в правильном порядке: сначала s3d, затем зависимые.
3. **Миграции базы только вперёд.** Откат на прежний exe возможен лишь с восстановлением `s3d.db` из резервной копии: данные, записанные после обновления, при откате теряются.
4. Рекомендуется обновить indexd до Smart Autopilot v0.4.1-rc.1. Режим размещения по-прежнему следует Autopilot Mode indexd (в Smart Active порядок хостов по Smart Overall, в Smart Shadow только журнал).
5. Новые настройки записи (`uploadRacing`, `uploadAttemptTimeoutSeconds`, `uploadHedgeBudget`) и буферов заданы значениями по умолчанию и ничего не меняют, пока вы их не поменяли.

## Проверено

- Сборка с `indexd next/indexd-v065@0c5dd34c` и `sia-storage-go next/host-errors@007f415`.
- Локальный s3d (рабочий ПК, почти пустая база): миграции 13 → 20 без ошибок, загрузка 200 МиБ и 700 МиБ через rclone mount, чтение 700 МиБ с хостов после очистки кэша, хеши совпали.
- Рабочий s3d на удалённой машине (около 1,4 тыс. объектов): миграции 13 → 20, чистый старт, тестовая загрузка 250 МиБ и чтение обратно (хеши равны), старый файл Acronis читается, хеш равен, плановая синхронизация rclone отработала с кодом 0.
- **Не проверялось:** набор s3-tests (tox), `snapshots restore`, снапшоты по расписанию на живых данных, object lock, теги и политики бакетов, поведение `uploadHedgeBudget` под нагрузкой, мультичастевая загрузка с контрольными суммами из логов.

## Известные проблемы и примечания

- **Релиз-кандидат.** Проверено на двух машинах Windows (рабочий ПК и удалённая локация).
- Для режимов записи подходят значения по умолчанию; `uploadHedgeBudget` и короткий `uploadAttemptTimeoutSeconds` стоит менять только под наблюдением `s3d status` и `smart-autopilot.log`.
- В Smart Active порядок строгий, но хост, который только что отказал (в том числе проиграл гонку более быстрому), на время пропускается, поэтому большая параллельная загрузка может распределиться по большему числу хостов, чем лучшие N.
- Отчёты о расходах оценочные: неудавшиеся и прерванные передачи не считаются, а стоимость вычисляет indexd по ценам хостов.
- Замечания предыдущих выпусков остаются в силе: лимиты передачи являются оценкой верхнего предела; перемещение или переименование объекта через S3 copy + delete может скачивать данные объекта из Sia (не исследовано); замеры скорости учитывают только успешные передачи, а скорость скачивания в основном отражает отклик хоста.
- s3d сначала принимает файл, а на хосты отправляет после; ограничение скорости клиента (например, `--bwlimit` в rclone) действует только на участок до s3d.
